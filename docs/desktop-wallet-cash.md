# Original wallet cash forms

`WalletCashOperations` repairs the original central administrative cash top-up and withdrawal forms. A permitted central administrator can credit a non-administrative user's wallet, or record a cash withdrawal. Both forms enforce their existing one-pound minimum and 5,000-pound maximum on the server, accept at most two decimal places, and choose the ledger's type, payment, status and party columns themselves. Cash top-ups represent external cash received; they preserve the original accounting rule and do not invent an application-wallet debit. Charging through Paymob remains a connected operation.

The desktop adapter additionally requires the current complete-administration snapshot authority: owner ID 1, or a current `Super Admin` role together with the original wallet-create and enrollment order-list grants. Other administrative snapshots deliberately omit wallet ledgers, so a wallet-create grant alone cannot establish the complete before-ledger. This restriction does not widen snapshot exports or change the ordinary connected browser form's authority. CRM directory and saved-delivery creators do not create `users`; a future offline account creator must expose a `wallet_account` identity mapping before dependent cash commands can be supported.

The service locks current actor authority, then the target wallet, before inspecting funds or creating any completed ledger row. A withdrawal with insufficient funds changes neither the balance nor the ledger or database notification. Decimal minor units avoid floating-point arithmetic. The existing top-up reactivation condition is retained. Only balance/status/timestamp columns change; the broad saved-user observer no longer recaptures an unrelated CRM profile as a side effect of moving money. Database notification creation remains in the same transaction, while the two notice classes defer their external pushes until after commit and omit those pushes locally.

`DesktopDashboardWalletCash` prepares the original `wallets.transfer` and `wallets.withdraw.store` forms with immutable command UUIDs, a complete ordered target-wallet ledger, balance/status/minimum and account identity facts. It invokes the actual original route, controller and middleware for replay. Saved replies require current enabled enrollment, the same current central account authority, and unchanged target identity; a historical successful reply does not require that the current balance still equal its historical result. Fresh replay requires the exact complete financial before-facts. Account, movement and legacy order references have separate types. Result verification compares the original amount, movement kind, balances, resulting status and command reference before an acknowledgement can be accepted.

The shared journal, command dispatcher, reference mapper, reconciliation and native reservation paths register only these two exact original forms. Their original DOM controls retain one immutable UUID after a lost submit. The local command clock is frozen to the journal occurrence so subsequent local commands retain replayable ledger timestamps. Current actor/enrollment/target identity are rechecked before both local saved redirects and native committed/aliased/terminal replies. `coverage.full_dashboard` is unchanged. No charging, order board, user-account or pending-application route is admitted by this component.

The standalone `tests/desktop_dashboard_runtime/wallet-cash.php` fixture runs actual Laravel and independent MariaDB connections with the uploaded schema shapes. It covers original-controller writes, immutable saved journal replies, changed UUID payload rejection, insufficient funds, malformed/overridden fields, exact rollback after controller work, stale balance and ledger conflicts beneath an older repeatable-read snapshot, typed reference validation, mismatching result refusal, warmed role/direct grant revocation, account/enrollment/identity changes, and two independent PHP workers racing to withdraw more than the shared wallet can fund. Its independent local/server database pair executes the shared middleware and reconciliation, real ledger ID drift, typed dependent cash commands, stale-server conflicts and native committed/aliased/cancelled response recovery. The fixture is included in the Linux and Windows runners; the local run does not establish installed Windows acceptance.
