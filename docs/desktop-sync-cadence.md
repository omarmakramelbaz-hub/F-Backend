# Desktop synchronization cadence

Automatic reconciliation starts at the first 30-second boundary after the desktop application is ready. One shared scheduler runs the retained POS ledger, uncertain server-outcome recovery and dashboard outbox sequentially. It never starts overlapping cycles or replays missed timer slots in a burst. If a cycle spans a boundary, that boundary is skipped.

Local writes remain immediate and durable. The renderer no longer requests synchronization after each action. Both native synchronization buttons queue the next scheduled cycle and return immediately; repeated requests share that cycle. Commands added while the dashboard outbox batch is being submitted wait for a later cycle, retaining their UUIDs and acknowledgment rules.

A request made during an accepted cycle joins that cycle's promise. If it requests a complete refresh, that flag is retained for the next free scheduled boundary and shown as queued; busy boundaries stay skipped. Closing cancels that flag along with other queued work.

Initial pairing may immediately read health and menu data, but this bootstrap cannot submit existing paid operations. Desktop preparation waits for the shared scheduled cycle before checking retained POS writes and open invoices. Shutdown cancels queued requests and future cycles, aborts active transports and preserves unacknowledged operations.

After verified preparation, the original dashboard pages use the local runtime both online and offline. Preparation switches to those pages immediately after the protected snapshot completes. Background reconciliation refreshes local data without returning forms to the server or requiring an active browser server session. An uncertain legacy server write still requires recovery before its local data can be activated. An absolute production URL from a local dashboard page is blocked rather than submitting outside the scheduled cycle.

Incoming updates use a separate delta path with the existing 60-second minimum between successful checks; uploads continue on the shared 30-second schedule. A private PHP CLI process captures the local baseline while the web process continues to accept local work. Only its bounded row-hash index is posted to the server. The response contains changed rows and a complete authorized media manifest. Reconstruction, required downloads, media reuse and full verification finish in an inactive database before the native view can be held. Added rows reach PHP in their original response bytes, preserving numeric transport.

Final replacement waits for the native idle checks. Only then does the application save the existing encrypted refresh intent and acquire the old database's durable write fence. Its fenced command sequence must still equal the captured sequence; a newly accepted local operation defers replacement and keeps the current generation. The final archive consumes the private preverified media seal, and activation moves the prepared pointer atomically. No server request or full media hash runs inside this final gate. Initial setup and explicit connected/manual compatibility flows retain their separate complete-snapshot path; an automatic delta failure never falls back to it.

An unchanged row, schema, media, enrollment, scope and executing-source response skips reconstruction and activation. Rotating media tickets and fresh response timestamps do not create a new generation. A minimal encrypted background capability is saved before temporary database creation. After a crash, the existing durable refresh intent is resolved first, then the retained runtime is verified before the application attempts cleanup of only this capability's unused capture and candidate. Private marker/token checks and zero accepted-command checks prevent deletion of an active database or journal. Positive database absence or discard precedes removal of its own temporary storage directory. An uncertain cleanup keeps the capability and prevents repeated background allocations.

Program exit aborts background transport and private CLI preparation. A final archive that already owns a durable fence is allowed to settle; recovery releases the old fence before shutdown completes. A failed or deferred incoming update cannot claim refreshed data or postpone the next upload slot.

Local acceptance covers exact timer boundaries, concurrent requests, slow and delayed cycles, failures, shutdown, arrival during an outbox batch, actual main-process pairing and packaged dashboard/preparation wiring. A new Windows build must execute acceptance against this source before installer delivery.
