# Existing GO store profile writes

The bounded candidate journals only the original `POST /admin/go-stores/{owner}` (`go-stores.update`). Its existing form/controller validates and saves the profile name, activity kind, address and revision, and atomically updates the owner's application commission. Existing enrolled profiles only: owner/account/product creation, credentials, images and other restaurant/store actions remain unregistered. `coverage.full_dashboard` remains false.

Every local, reconciliation or reserved native request proves the current enrolled actor/device and `gs:{owner}` membership before returning a saved reply. Original authority is an admin account with either ID 1 or both current `resturant-list` and `resturant-edit` grants. Role names do not replace these grants. The original controller does not exclude an admin with `owner_resturant_id`; its target accepts a GO vendor or a delegate whose current pending application identifies a store owner, without an accepted-status condition on that target.

Before-facts contain the complete profile apart from timestamps, the nonsecret owner eligibility fields and canonical previous commission, and the delegate's pending profession/linkage. Named `menu_store_owner` references share the existing reviewed availability identity mapping; other entity kinds are rejected before resolution. The original revision read now locks the current profile row inside its existing transaction, including under an older repeatable-read snapshot. Original controller validation and redirects are retained. A journal or receipt failure must roll back both profile revision and commission.

For scoped administrators, the deployed `users.pending_vendor_id` has no foreign key. Snapshot export therefore closes only the eligibility link of an existing enrolled GO delegate: the original pending ID, profession, type, status and source application. Required `full_name` and `mobile` are explicit empty strings for the unchanged original DDL; all nullable application, identity, payment and address fields and PendingVendor media are omitted. Existing table row SHA-256 covers that exact projection, and `coverage.pending_vendor_eligibility` records its IDs, source fields, required redactions and `application_review: false`. These rows support only the original Catalog eligibility predicate. Application review reads are incomplete and pending application writes remain unregistered; the redacted required values never enter GO before-facts. Full administration snapshots retain their existing complete pending rows. Neither scope claims complete dashboard coverage.

The original shared form hook adds one immutable UUID to this exact POST path and retains it after a lost reply. Header and form UUIDs may supply the same command; inconsistent aliases conflict. Native reservations cover this exact existing-owner POST and preserve terminal recovery. Acceptance and native/browser evidence must be reported against the final frozen source; registering the route alone is not proof of usable whole-store CRUD.

Acknowledging an already committed native GO status also requires the current original administrator grants and the current enrolled `gs` owner parsed from the immutable reservation path. Revoked grants or enrollment retain native uncertainty until restored. This status is metadata only: it does not replay a business reply or require the past profile to still exist. Returning an original saved redirect continues to require full current target eligibility.
