# Customer app WhatsApp choices

`POST /api/user/whatsapp-consent` records explicit choices from the authenticated Fasakhansta customer. It uses `auth:api`, `app.scope` and `custom.jwt` and never accepts a target phone, customer ID or staff actor from the request. The service reloads and locks the account and uses its currently stored phone. Changing a phone does not copy the old phone's consent.

Send the existing bearer token with the Fasakhansta app scope (the existing missing header default or `X-App-Scope: fasakhansta`). Generic GO Customer, GO Partners, merchant, staff and declined accounts cannot use this endpoint to opt in to Fasakhansta messages.

```json
{
  "whatsapp_consent_version": "2026-10-17.v1",
  "service_consent": true,
  "marketing_consent": true
}
```

Both purpose fields are optional. Omit any purpose that the customer has not selected; an explicit `false` revokes that purpose. A version-only call changes nothing and does not create a directory profile. The exact version is required on every request. JSON booleans and form values `1` / `0` are accepted; an empty or null choice is rejected. Unknown fields are rejected.

The API returns the usual `{ "status": "Success", "data": ... }` envelope with the current `service_consent`, `marketing_consent`, `opted_out_at`, `whatsapp_consent_version`, and whether a choice changed. Evidence is generated by the server as a customer self-choice from this authenticated app form, including its version, scope and current user ID. The recorded actor is that customer, not a cashier.

The app should show separate, unchecked feedback and promotion choices near the phone field. After successful authentication it can submit only choices the customer selected, using the new bearer token. Merely entering a phone or authenticating must not send this request with positive choices. Network errors must not report a successful opt-in or prevent the underlying login. There is no automatic retry: a lost acknowledgement requires the customer's next explicit action.

An incoming WhatsApp STOP remains effective until a new explicit positive choice. Re-enabling one purpose leaves the other purpose disabled. These choices do not send messages, fabricate a purchase, or enable the dashboard's messaging configuration.

This backend source alone does not update installed mobile apps. The corresponding Fasakhansta Flutter form and authenticated submission must be included in a separate app release. No Fasakhansta opt-in is solicited during generic GO Customer registration.

Verification: `CRM_TEST_AUTOLOAD=/path/to/vendor/autoload.php php tests/customer_app_consent_test.php` uses the real CRM SQLite migration, service, controller and API route files without reading `.env` or contacting WhatsApp.
