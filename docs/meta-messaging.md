# Native Meta messaging for Fasakhansta

The `/admin/meta` inbox uses the same chat, per-user unread markers and order-review interaction as WhatsApp, with All / Messenger / Instagram filters. Central Owner/Admin access is refreshed from the database; branch accounts cannot read private conversations. Replies, orders and receipts are scoped by channel, business account and native customer ID. A phone mentioned in chat is an order contact, never a reason to merge conversation identities.

Signed `page` and `instagram` envelopes arrive at `/api/meta/messaging/webhook`. Only configured accounts are stored. Raw events, customer identities, messages, extracts and reply audits are encrypted. Acknowledgement follows durable persistence. Projection handles inbound messages, native business echoes, standby copies, text, media indicators and native locations. Replays do not duplicate messages. Conflicting capture remains quarantined.

The order service shares the deployed WhatsApp workflow through channel hooks, with independent Meta tables, leases, cutoffs and confirmation keys. The AI extracts evidence and sends no replies. Grounded matching confirmation, complete customer/product/branch/location data, business hours and canonical POS/delivery quotes govern automatic dispatch. Existing branch-customer, unpaid phone-order and kitchen/printing services handle the order. Missing business echoes and ambiguous data remain for review. External Business Agent prompts, schedules and settings are unchanged.

Manual text replies use the account token, native recipient and standard 24-hour response window. Durable UUID claims prevent repeated sends. Uncertain delivery blocks a subsequent send; it never retries automatically. The Meta inbox has its own chat assets, preserving the installed WhatsApp screen. Incoming photos open in a lightbox; audio/video have native playback and documents have download links. Users can copy text, forward an explicitly selected text/media part to another conversation on the same business account, and delete a message from their own dashboard. Per-user tombstones leave original capture, unread chronology and order evidence intact. Manual forwards use the same recipient/window/UUID controls as replies.

Uploads support validated photos, MP4 video, audio and Messenger documents. Voice recordings are inspected and converted to AAC M4A, with a 60-second/8-MB input limit; ffmpeg/ffprobe are required. Native attachment upload is used for Messenger and Instagram with Facebook Login. Instagram Login receives a private prepared file through a signed ten-minute URL. Only validated media is exposed; files live outside the web root and expired staging is purged. Uploads never send messages. A customer-send uncertainty marker is persisted before the send, and uncertain requests are resolved by UUID without an automatic retry. Instagram document uploads are unavailable. File/media type availability is returned to the picker.

## Installation and accounts

Use the pinned root helper. The incremental installer checks installed WhatsApp workflow/UI blobs, backs up replaced code privately and preserves unrelated installed route/menu changes. It migrates only the six Meta migrations, rebuilds existing caches and verifies routes. Unknown blobs fail before writing. Failure restores code/caches without dropping additive tables or deleting captured data. It does not reset a branch or overwrite credentials.

Route verification directly checks all twenty-five Meta routes, controller methods, HTTP methods, actual request matching, API exclusions and dashboard access/session middleware. It avoids Laravel 8's broad `route:list` inspection, which can resolve unrelated controllers before applying its path filter. An actual Meta verification failure still restores code and reports structural diagnostics; raw PHP output remains in a private backup log. After a failed installation, retrying leaves the already applied migrations in place.

The dedicated service runs as `fasakha`; its timer waits 30 seconds after the previous invocation. Each run projects up to 500 events and processes up to ten threads. A worker lock prevents overlap. The WhatsApp timer is untouched. Automatic dispatch remains independently configured.

Configure credentials through hidden SSH terminal prompts:

```bash
cd /home/fasakha/public_html
runuser -u fasakha -- /opt/cpanel/ea-php82/root/usr/bin/php artisan meta:configure
runuser -u fasakha -- /opt/cpanel/ea-php82/root/usr/bin/php artisan config:cache
```

Enter the App Secret for the app subscribed to both webhook objects. Messenger needs the Facebook Page ID and Page access token. Instagram needs its professional account ID and either an Instagram-login token or its connected Page's Facebook-login token; select the matching login type. The command prints the callback and verify token. Credentials stay in `storage/app/private/meta-messaging.json` with mode 0600 and are never committed or requested in chat.

Register this callback under the app's Page/Messenger and Instagram webhook settings, preserving the WhatsApp callback. Subscribe Messenger messages and message echoes, and Instagram messages. Attach the actual Page/Instagram account to the app; callback registration alone does not attach an account. Complete the required messaging permissions/access for real customers. Instagram with Facebook Login requires a professional account linked to its Page. Instagram Login uses `instagram_business_manage_messages` and does not require a linked Page.

Verify an incoming message and a native business reply in the same thread on each channel before automatic orders. Configure the existing WhatsApp extraction credentials, automation actor and allowed branch IDs first. Establish independent Meta cutoffs:

```bash
systemctl stop fasakhansta-meta-messaging.timer fasakhansta-meta-messaging.service
cd /home/fasakha/public_html
runuser -u fasakha -- /opt/cpanel/ea-php82/root/usr/bin/php artisan meta:configure --activate-orders
runuser -u fasakha -- /opt/cpanel/ea-php82/root/usr/bin/php artisan config:cache
systemctl start fasakhansta-meta-messaging.timer
```

Activation drains a bounded historical capture before recording new cutoffs. Capture failures block activation; delayed historical messages fail the existing event-time guard. Agent reply settings are unchanged.

## Missing incoming messages or customer names

Business echoes alone prove outbound capture, not inbound delivery. The normalizer accepts native incoming messages and standby copies; an echo-first conversation joins the later incoming message by the same channel, account and native peer. Only a genuine recent inbound message opens the reply window. Historical messages from before a working subscription are not fetched by this webhook feature.

Meta documents `message.admin_text` as business-facing handoff context. An administrative notification may arrive without the underlying message, so `mid` and `text` can be absent. An exact `admin_text`-only object with valid native routing, timestamp and notice text is ignored while its encrypted raw capture is preserved. It creates no message, conversation, unread state, reply window or order evidence. A native message containing administrative metadata still projects normally; other unkeyed or malformed shapes remain quarantined. See the [Messenger messages reference](https://developers.facebook.com/documentation/business-messaging/messenger-platform/webhooks/webhook-events/messages) and [Instagram messaging webhooks](https://developers.facebook.com/documentation/business-messaging/instagram-messaging/webhooks).

For the reviewed installation, use `deployment/apply_meta_admin_notices_root.sh` with its pinned release. This separate updater changes only `MetaMessagingProtocol.php`, verifies the prior protocol and unchanged access/consumer blobs, stages PHP syntax and protocol checks, and keeps a private rollback copy. The wrapper pauses only its owned Meta units and restores each unit's previous active state on exit. It resolves only the five reviewed Messenger capture IDs `5,12,13,18,22` for Page `118160256722323`: the complete decrypted envelope, stored hash and original `INVALID_EVENT` marker must match strict administrative-only guards. A durable private audit records the prior markers before a transaction marks those captures processed and removes their mistaken quarantine markers. Raw payloads and message/order/read data are preserved. Mixed, changed or unfamiliar envelopes fail closed. An already-resolved run writes no database changes.

The helper finishes with the read-only inbound diagnostic. Administrative notifications have separate raw and normalized counters and do not increase incoming-message or standby-message counts. This repair corrects notification classification; it does not recover customer text that was never captured or resolve a rejected profile GET. The earlier chat/profile installers retain their frozen foundation hashes and intentionally reject this newer protocol rather than silently overwriting it.

Customer display names are enriched separately through the native user-profile GET API. Messenger uses the customer's Page-scoped ID with its Page token; Instagram uses its scoped ID and the configured login/token type. Responses must identify the same native peer. Names and retry metadata remain encrypted, known names are preserved, and failed profile requests are throttled. Profile lookup runs after capture/order work and never supplies order facts or opens a response window.

For an existing installation, use `deployment/apply_meta_chat_root.sh` with the pinned release. The feature updater validates old file hashes, publishes only the listed Meta files, applies the new additive hide migration, rebuilds the existing routes cache when needed and verifies all twenty-five routes. It preserves shared WhatsApp files and the native sidebar. The dedicated Meta timer is restarted if it was active. Code/routes cache are restored after verification failure; additive tables and captured data remain.

The separate profile-only `deployment/update_meta_profiles.py` remains available for a profile-only upgrade. This narrow updater stages and lints three profile-related files, validates the known prior worker blob and unchanged Meta foundations, checks the existing encrypted storage, and keeps a private rollback copy. It does not reinstall the inbox or modify shared WhatsApp code, routes, credentials, caches, subscriptions or automatic-order settings. The original full feature installer also accepts only explicitly pinned previous feature blobs when upgrading.

The `meta:refresh-profiles --limit=10` command fills missing display names without processing orders or sending messages. The regular Meta timer continues filling names for later conversations.

Run `deployment/meta_inbound_diagnostic.php` from the application working directory as its user. It prints raw capture versus normalized incoming/outgoing counts, pending/quarantined events, bounded name-availability counts, timestamps, and read-only app/account subscription checks. No customer names, peer IDs, message contents or tokens are printed. Sampling limits and completeness are explicit; a zero incoming count in an incomplete sample cannot prove that no inbound event has ever arrived. Graph failures are reported as fixed categories rather than raw error bodies. This diagnostic never changes subscriptions or thread control. Use its results before recommending an unavailable `standby` setting or a routing change.

When the capture lacks `message.mid` or profile lookup returns `100/33`, run `deployment/meta_event_identity_diagnostic.php` from the application directory as its user. It reads at most fifty captured envelopes and twenty message shapes, with explicit completeness/omission counts. Fixed field types, identifier lengths and projected-peer overlap are reported without native IDs or message values; unknown keys are counted without printing their names. A fixed equality flag for the test text `Hello world` is only a clue, not proof that an event is synthetic. Instagram change/event categories explain captures that contain no messages. Bounded Graph GETs compare the saved token's app and Page identities and whitelisted scopes. Facebook-login Instagram tokens are checked against the configured Page and its linked professional account; a Page identity is expected rather than the Instagram account itself. Advanced Business Asset User Profile Access is a separate feature, not one of these scope booleans. No data, account settings, caches, subscriptions or quarantine markers are changed.

Missing native message IDs must remain quarantined unless the event is the validated administrative-only notification described above. Do not generate message IDs, substitute unrelated fields, or replay incomplete evidence into replies or automatic orders. `100/33` alone does not establish which permission, token or peer identity caused the profile rejection.

For an object containing only an unrecognized field, `meta_event_identity_diagnostic.php --message-flags` returns a compact local-only report, without Graph calls. A fixed list of extra field candidates is classified by type, safe boolean values and fixed nested field types. String candidates expose their length and whether they contain a JSON object; only the types of five fixed nested fields are reported. These candidates are diagnostic checks, not supported message formats or permission diagnoses. Other fields expose key length/type, a SHA-256 fingerprint of the key only, and string-value length, capped at eight per message with an omitted count. No value is hashed; arbitrary key names, text, identifiers and nested values remain hidden. A key's length alone cannot establish that it is a ciphertext field or establish an encryption/recovery method.

The separate `deployment/whatsapp_order_file_metadata.py --root /home/fasakha/public_html` diagnostic identifies owner/type blockers for the frozen WhatsApp order-evidence repair `425ccb37`. Run it as `fasakha`. It only reads filesystem metadata for that repair's fixed candidate paths and bounded direct config entries, rejects symlink traversal, and prints no file contents. It does not apply either WhatsApp or Meta updates. Diagnose the reported path before changing any ownership.

After the live diagnostic confirms `config/go_services.php`, `config/jwt.php`, `config/mail.php` and `config/partner_auth.php` are regular `0644` files owned by root, the root-only `repair_whatsapp_order_config_owners_root.py --root /home/fasakha/public_html` repairs only their owner/group to the application account. It validates every target before changes, holds the existing installer locks, preserves bytes/mode, creates a private metadata/hash journal and guards rollback against concurrent changes. Already-correct files are unchanged. Then retry the original frozen WhatsApp order-evidence repair; no Meta parser or subscription change is implied by the owner repair.

## Owned-business Facebook Login

`/admin/meta/connection` lets the persisted central Owner authorize the existing Fasakhansta Page and its linked Instagram account using Facebook Login for Business. The Owner policy matches the POS owner foundation: user ID 1 or the persisted `Super Admin` role with the `admin` guard, after the normal central inbox access check. Branch users and ordinary administrators cannot manage the connection.

The integration uses app `2177982783065133`, configuration `3007667439572336`, and Graph `v25.0`. The installer derives the canonical HTTPS callback from the server's `app.url` and prints `redirect_uri` and `connect_url`. Add that exact callback to **Facebook Login for Business → Settings → Valid OAuth Redirect URIs** before clicking the connection button. The OAuth callback path is `/admin/meta/connection/callback`; the existing message webhook remains a separate route.

The flow is POST start → Facebook authorization → GET callback → review permitted accounts → POST confirm. Start and confirm use the existing web CSRF protection and the dashboard's `data-spa-off` marker for native form navigation. The authorization redirect must navigate the browser to Facebook; sending this form through the dashboard SPA fetch prevents that transition. State and encrypted pending credentials expire after ten minutes and are bound to the persisted Owner and current app/configuration/callback. The callback scrubs its parameters from the application request, disables debugbar on connection routes, and redirects to a clean connection URL. Only account labels and channel/account IDs enter the review page.

Discovery validates the user token and lists only business identities already present in the native Meta account configuration. Confirmation rechecks each selected Page token's issuing app, identity, scopes and linked Instagram identity. Page subscription fields are read, preserved, merged and verified; it does not change app-level webhooks, another app's subscriptions, Business Agent configuration, orders or customer messages. A failure leaves the locally saved credentials unchanged; a timed-out Meta subscription write can have reached Meta and is reported as a failure without an automatic retry.

`storage/app/private/meta-oauth/settings.json` is private configuration. `credentials.json` contains an encrypted credential bundle; the directory is mode `0700` and files are `0600`, owned by the application account. New tokens overlay only matching native identities. Unselected credentials are preserved, and unavailable or corrupt overlay files fall back to the native accounts. The original `meta-messaging.json` is unchanged.

Deploy using the pinned `deployment/apply_meta_oauth_root.sh` helper with a full release SHA. Its Python installer validates the observed live foundation hashes, stages and lints the narrow source set, backs up affected originals outside the public web root, publishes settings last and verifies the four routes and compiled Blade views. It rejects unexpected source changes, unsafe paths and cached routes; failures restore its own changes while preserving later operator edits. No full checkout, database migration, timer change or Graph request is part of installation.

Validation: `tests/meta_oauth_controller_test.php`, `meta_oauth_privacy_test.php`, `meta_oauth_credentials_test.php`, `meta_oauth_service_test.php`, `meta_messaging_routes_test.php` and `meta_oauth_install_test.py`. The PHP component tests use `WA_INBOX_TEST_VENDOR` pointing to an isolated Laravel 8 Illuminate vendor directory; they do not contact live Meta. After installation, complete real Facebook authorization and a Messenger/Instagram receive-and-reply test before recording the App Review screencast.

## Message hub (14 October 2026)

The main sidebar shows one Meta inbox. Its channel tabs link to WhatsApp at `/admin/meta/whatsapp`, while the existing `/admin/whatsapp` routes continue to serve the WhatsApp worker, reply and order modules. The WhatsApp channel retains its central Owner/Admin access checks and its own conversation/message IDs.

WhatsApp received and accepted outgoing audio now have same-origin media players. The existing authenticated media service resolves the media ID, checks the receiving phone, provider size and SHA-256 digest, downloads only from approved provider hosts, checks the detected MIME, and rechecks message visibility after download. Audio downloads have a 16-MiB limit. Recording still requires the browser microphone permission, an open customer response window, and the existing ffmpeg/ffprobe runtime. Recordings are reviewed before sending.

Message deletion hides messages from the acting administrator's dashboard and blocks their media download. Customer/provider copies and order evidence remain intact. Existing WhatsApp bulk deletion and Meta message actions remain available.

Opening an unnamed Meta conversation requests one scoped user profile with the current saved account token. The returned social name is shown only when the provider confirms the same customer ID; missing names keep the existing fallback. Profile failures are throttled and do not block the message feed. Meta audio/video elements are retained across live transcript updates to preserve playback.

`deployment/apply_meta_message_hub_root.sh` installs only seventeen pinned feature files and adjusts the two existing sidebar hooks in place. It keeps a private backup, checks PHP and Blade syntax, verifies authenticated routes, reports voice-runtime readiness, and restores published files if verification fails. It does not change OAuth credentials, account subscriptions, message/order tables, automatic reply settings or worker activation.
