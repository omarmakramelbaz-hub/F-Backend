# Original dashboard local runtime — implementation checkpoint

The requested product is the complete original dashboard in an installed Windows application: the same Blade pages, account permissions and business services, local operation during an outage, and complete reconciliation when service returns. The released 0.2.1 installer does not implement that product. This checkpoint is unfinished and must not be described or deployed as a completed full offline dashboard.

## Implemented and verified

- The complete original Laravel 8.83.29 application boots with its original routes in a private desktop storage directory. Production environment files and caches are excluded.
- Original business changes and encrypted command records commit in the same InnoDB transaction. A forced journal insert failure rolls back stock and financial changes.
- A separate account enrollment credential retains current server branch and account authorization. Revocation is checked before replaying an old result.
- Server imports dispatch to original business services, deduplicate stable command UUIDs, and map locally created entity IDs to server IDs. Nine linked flows are verified: goods receipt, cash sale, approved cash expense, employee creation, attendance, payroll advance, shift closing, payroll closing and payment confirmation.
- Eight additional catalog actions invoke the original category/product controllers, permission middleware, FormRequests and repositories: creation, update, single deletion and bulk deletion for each catalog. Original form redirects and validation errors are preserved. Category/product IDs and portion features reconcile despite integer ID collisions. Revoked permissions and changed server rows reject a change without discarding its local command.
- Four original area actions use the same controller replay and journal: creation, update, single deletion and bulk deletion. Created parent/child area IDs map independently of colliding server IDs; changed selected rows and revoked original permissions prevent deletion. Original area fields and page redirects are retained.
- Four original FAQ actions retain their FormRequest, repository, Arabic/English HTML answers and single/bulk deletion. The request file now follows its existing class name, and the original bulk URL targets its actual permission-protected method. Mapped ID collisions, changed answers and current deletion permissions are covered by actual HTTP/controller fixtures.
- Original single/bulk contact-message deletion is journaled and reconciled with complete row comparisons and current permissions. Private contact messages stay outside branch snapshots; the primary administrator imports its original global messages. Changed messages reject pending deletion without removing any selected row.
- Shift import compares the complete mapped financial review before reissuing its server HMAC. The local and server application keys are different. Local secrets do not become production secrets.
- Payroll closing compares the mapped employee, salary totals, attendance and entry facts before issuing the original server preview fingerprint. Database-local attendance/audit IDs are excluded; actual entry/employee references and semantic revisions are retained. Changed server attendance rejects the close without a server payroll or payment. Lost local shift/payroll replies reuse their encrypted approved facts, including the same typed dependencies, after the first operation changes the ledger. Original payroll payment remains an accounting confirmation, rather than a bank transfer or a cash-drawer movement.
- Initial data export uses explicit table and branch rules and a consistent read transaction. Other branches, device journals, pairing credentials and server sessions are excluded. Only the enrolled user's password hash is retained for the original login mechanism; other included accounts cannot log in.
- Import validates data and schema hashes and foreign references in a new local staging database. Setup refuses to overwrite a populated database. The imported database gets its own empty encrypted journal.
- Initial import durably binds the local snapshot, account, branches and incomplete coverage to a local state row. The native-only `refresh-begin` control acquires the same InnoDB row lock that original business writes acquire before resolving references or changing data. It refuses every unconfirmed command, including conflicts that leave no sendable outbox page. The fence survives restarts, stores only a hash of its native capability, and has no automatic expiry. `refresh-cancel` restores writing without deleting business rows or journals. Durable attempt history makes old begin/cancel retries harmless even while a newer fence is active. Native recovery can inspect an existing attempt without reacquiring its fence. The generation refresh described below extends this boundary; the production dataset still cannot receive a completed preparation marker. Older local datasets without this state fail closed; they must be upgraded while retaining their pending journals.

The exporter now covers those reviewed table structures, with explicit empty credential/queue schemas and scoped business rows. Foreign-key parent closure resolves legacy cycles without automatically importing unrelated financial ledgers. - The original branded login authenticates the imported enrolled account through the unchanged controller. Actual HTTP tests render original home, takeaway, phone, dining, inventory, employee, expense and owner catalog pages and serve their original styles/navigation scripts locally. Calculating a price through original POST endpoints works without queuing a write. Uncovered GET mutations are blocked by a real read-only transaction.
