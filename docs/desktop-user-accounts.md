# Bounded original account controls

Only `users.change-status`, `useraddresses.destroy` and the public-name subset of `users.update` are registered by these increments. `coverage.full_dashboard` remains false. Account creation, other profile/password/role editing, account deletion, bulk deletion, GO driving reactivation, mobile changes, customer status changes and identity-document media remain outside this adapter.

The original status GET runs its unchanged controller for `admin`, `vendor`, `delegate` and `resturant_owner` accounts. Only `accepted` and `declined` are accepted. Owner account 1, protected account 560 and the enrolled actor itself cannot be changed. The accepted transition preserves the original expiry reset. Application-customer status is withheld because its User observer captures the shared CRM identity and every existing legacy/GO order branch; this increment does not infer those missing branch facts.

The original address DELETE removes only an unused address. It locks the selected row and checks every declared incoming foreign-key relation, plus the legacy order relationship. A real `orders.user_address_id → user_address.id` foreign key is required. Any referencing row rejects the deletion, regardless of whether the deployed constraint uses CASCADE or RESTRICT. The fixture's synthetic delete action is therefore not treated as evidence of the production constraint's action. Address deletion does not fire the original saved-address observer.

Both controls require the current enabled enrollment, a current central administrator (no restaurant reassignment), and the complete-account import cohort: account 1 or the persisted `Super Admin` role. Other members also need the target account type's current `-edit` grant for status or `-delete` grant for address removal. Checks use locking reads rather than warmed Spatie relationships. Every original base enrolled branch must still exist structurally. GO administration deliberately permits its owner's declined status while retaining the current profile, account kind, app scope and pending store-owner profession: declining an account cannot prevent recovering that decline's immutable reply or explicitly reactivating it. This does not change POS branch availability or admit a later catalog capability as account-administration enrollment.

Before-facts include every public User column, the complete ordered target role/direct memberships, and the selected complete address when relevant. Credential hashes, tokens and private columns never enter account commands. These two original actions do not write credentials. They compare identity fields including `created_at` before saved replies; changed public before-facts conflict before new work. These identity fields detect ordinary replacement, not a database administrator deliberately reproducing the same ID and timestamp.

Original SQL/controller effects and the encrypted command/result commit in one transaction. Immutable UUIDs remain on the original status links and DELETE forms after a lost response. Local and independent central replies deduplicate without repeating the controller. The result emits only explicit `dashboard_user` and `wallet_account` aliases bound to the selected User. Typed references translate complete before-facts and dependent targets, including a real 40→40000 ID difference in the integration fixture. That prior identity receipt is explicitly seeded; it is not acceptance evidence for a User creator.

Connected native transmissions use the same reviewed controls through durable transport reservations. Both the logical DELETE and the original POST method-override address envelope are supported. Terminal recovery and aliased retries recheck current administration, module permissions, target identity and base enrollment before disclosing a saved result. Unknown outcomes retain their reservation; cancellation fences delayed requests. HEAD cannot execute the status action.

Validation: `tests/desktop_dashboard_runtime/user-accounts.php` and its reconciliation fixture run the actual original Laravel controllers, middleware and User observers against disposable MariaDB. They cover exact retries, changed bytes/UUIDs, current authority/enrollment revocation, protected accounts, reference binding, complete profile conflicts, older repeatable-read races, rollback, real address/order FKs, independent local/server IDs, dependent timestamps and native terminal decisions. Node fixtures cover original form/link UUID retention, native durable reservation recovery and dashboard uncertainty classification. These tests do not establish complete User CRUD, Windows browser/installer acceptance or full-dashboard operation.

## Original public-name update

`users.update` now accepts a name edit for the same non-customer account cohort. The original PUT/PATCH route, `StoreUserRequest`, controller and User Eloquent save run. A server-only, reentrant repository context selects this reviewed name-only branch before the legacy repository's credential, role, pending-vendor, media and financial branches. No request flag activates that context; it is restored on every return and exception. The unrestricted connected repository path is unchanged.

The actual original form keeps its frozen account-type, mobile/email, role, pending-link and financial controls for validation. Changing them is rejected. Empty password controls are accepted; nonempty credentials, uploads, supplied IDs/timestamps and unreviewed fields are rejected before journal work. Pending descriptive/document fields must also retain their existing values. The local/prepared-native form explains this boundary. Only the User name and original Eloquent timestamp change. Complete public User, memberships and any existing pending application are compared before work and verified afterward. User observers remain in the same SQL transaction. A separately changed server password survives this noncredential update unchanged, without exporting a password proof or deriving one from a native placeholder.

The actual original current account-type edit permission applies even to owner account 1, before both new and cached profile replies. Local, independent central and native reserved requests use the same immutable UUID/name and typed User aliases. Tests exercise original form/controller validation, genuine User ID drift, credential preservation, forbidden field smuggling, current permission revocation, lost replies, observer-triggered rollback and nested exceptional context restoration. No proof is claimed for the unrestricted legacy updater or other public fields.
