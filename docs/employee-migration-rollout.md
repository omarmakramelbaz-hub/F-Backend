# Employee identity migration and release gate

The employee change adds nine nullable columns to `branch_employees`. Deploy the reviewed migration with the application files, then run only `2026_10_23_200000_add_employee_identity_and_regulation.php`. Never run every pending migration, delete a migration-ledger row, or invoke `migrate:rollback` as recovery. MySQL DDL can commit independently of an Artisan failure. Retained nullable columns are compatible with the previous code.

`deployment/go_erp_employee_migration.py` is a pinned package helper. Its adjacent `verify_go_erp_employee_schema.php` is pinned separately. The caller supplies the exact Git blob IDs from the final reviewed release, not a branch name or a newly calculated live-file hash. Package code and probe must be root-owned; the application migration may be owned by root or `fasakha`. Symlinks, hard-linked files, unsafe directories, unknown host, changed lock and an active watcher are refused.

The existing program deployment adapter should integrate these steps while holding its real `watcher.lock` and with both timer and worker quiescent:

1. Validate the supported Preview35/wire predecessor cohort, source pins, history and monotonic version/sequence floors as before. Prepare and apply the reviewed application patch, including the migration. Reverify the source.
2. Call `execute(package, audit_parent, MIGRATION_BLOB, PROBE_BLOB, True, lock_fd, verify)` from the pinned helper. `audit_parent` is an existing root-owned `0700` deployment audit directory; `verify` revalidates the existing watcher lock. The probe is passed over STDIN to PHP as `fasakha`, so private package/audit directories remain inaccessible to that account. Raw PHP/Artisan output is retained in `0600` private audit files and never copied into terminal errors.
3. The helper checks column types, lengths, nullability, unsigned acceptance actor and the one migration-ledger record. It accepts an unrecorded partial schema only for the reviewed per-column idempotent migration. A recorded partial schema is refused. It runs the absolute ea-php82 binary as `fasakha`, in the fixed application directory, with `artisan migrate --force --no-interaction --path=database/migrations/2026_10_23_200000_add_employee_identity_and_regulation.php`. It then repeats the metadata-only checks.
4. If `ok` is false, retain application and schema audit evidence and leave the timer paused. Never start a build, publish a feed or drop columns. Source rollback may preserve the nullable additions; report that explicitly. A caller must not replace the helper's `database_changed` result with `false` merely because source/watcher rollback succeeded.
5. On success, complete the program watcher/source migration but leave the timer paused and do not start its worker. Retain existing release history, installer files, publication sequence and version floors. Do not relabel the old release as the new source. Existing update endpoints already hide installers whose source/GUI fingerprint no longer matches.

The helper's `database_changed` is `false` before a migration attempt, `true` when verified metadata/ledger changed, and `"unknown"` after an unsuccessful attempt whose effect cannot be established. A fully verified no-op is `false`. `schema_rollback_attempted`, `watcher_started` and `published` are always false. Every created audit is retained on success and failure. This helper does not certify browser or Windows acceptance.

Build a candidate as a CI artifact without publishing it to the live feed. Before enabling publication, require separate retained evidence for both the authenticated browser and installed Windows candidate: employee listing/status, authorized front/back upload and retrieval, inaccessible photos from another branch/account, correct regulation version acceptance, disconnected behavior, and existing cashier sale/expense/inventory/shift plus reconnect synchronization. Include the incremental migration from an old generation in the desktop test. No evidence file should contain a real identity photo or account row value.

The root-owned release-gate receipt must bind the exact reviewed core commit, candidate commit, live source fingerprint, candidate inventory SHA-256 and installer SHA-256. Its browser and Windows entries must identify the actual executed evidence artifacts and their SHA-256 hashes, with explicit passed results and execution times. The publisher must recheck those identities immediately before publication. Neither this migration helper nor deployment tests may create a passed browser/Windows receipt. Missing, failed or mismatched evidence keeps publication paused; a missing real VPS/Windows connection must be reported as untested.

Only after both actual acceptance checks pass should a separate pinned release step enable/start the watcher. Normal CI acceptance, source matching, monotonic version/sequence checks and the existing two-cohort guards remain mandatory. A successful database migration alone never opens the publication gate.
