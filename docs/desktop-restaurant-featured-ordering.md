# Original restaurant featured ordering

The desktop adapter adds only the original `POST /admin/update_sorting_is_featured/{resturant}` route, named `update_sorting_is_featured`. It executes `ResturantController::update_sorting_is_featured` against the original scoped `Resturant` model. The operation updates `sortby_is_featured` and the normal Eloquent update timestamp, returns the original restaurant-list redirect with its `page` input, and retains the original success flash. It shares the reviewed `DesktopDashboardRestaurantFlags` journal with the two restaurant checkbox routes.

The original custom sorting action has no `resturant-edit` controller middleware. The adapter preserves that source behavior: the current enrolled actor and enabled device must still own the current enrolled F branch, the original `IsAdmin` middleware and current original controller middleware execute, and implicit model binding must resolve the same scoped restaurant. It does not infer an extra resource permission from the sorting control's appearance in the role-11 list page. Authorization runs before saved local replies, server replay receipts, native saved replies, and committed-outcome recovery.

The exact serialized input is retained. `sortby_is_featured`, `page`, and the immutable operation UUID are the only accepted business payload fields. The browser's existing numeric input keeps its `min=1` and `step=1`; replay does not replace the original controller/database semantics with a new positive-integer rule. Missing input persists NULL, and ordinary online legacy submissions retain their existing semantics. Local writes require a valid UUID; contradictory form/header UUIDs, changed content under the same UUID, extra fields and unexpected uploads reject before mutation.

Before execution the adapter locks and records all 29 inspected restaurant columns, its added-by and owner identities, optional parent identity/ownership, and its enrolled F branch. Replay rejects changed before-state or ownership relationships. The receipt captures the actual complete result and compares server/local after-state, excluding only normal write timestamp timing. Creation identity and every other column remain exact. Named typed restaurant, user and area references are resolved only through accepted preceding receipts; a dependent numeric sort may target a mapped restaurant without writing a colliding local ID on the server. Foreign entity kinds reject before reference resolution.

The command and controller write commit together. The native remote-attempt path stores the exact encrypted before/after facts and HTTP outcome in the same transaction as the original write. A lost response can reuse the same command UUID, and a cancelled attempt cannot later execute an original delayed POST. Saved replies retain current actor/device/branch checks. Existing checks verify the required tables use InnoDB before native reservation.

The source-bound fixtures extend the real local HTTP/journal/reconciliation tests with numeric sorting, a changed-number UUID conflict, extra-field rejection, a before-state conflict and typed mapped replay. Native HTTP fixtures include sorting in the original-response retention, current authority/revocation, atomic rollback and terminal-cancellation scenarios. The Windows Edge fixture exercises the original numeric input and submit button: commit 7 while dropping its response, reject 8 under the same UUID, retry 7, then accept 8 under a fresh UUID after navigation. It retains the two existing checkbox flows. The expected browser receipt has six commands and 29 checks. Fixture presence and static checks do not establish a successful actual Windows run; that CI receipt remains required.

Restaurant operating-status changes, global control, restaurant CRUD and product/media administration remain outside this increment. `resturants.updateStatus` broadcasts `ResturantUpdated` through the original repository and needs provider/queue review. `resturantControl` is a GET mutation over the currently scoped restaurant selection, excluding ID 82, so it needs exact selected-row membership facts and a separately reviewed mutation path. Restaurant create/update replaces delivery areas and mutates Spatie media files outside ordinary database rollback; delete/bulk delete also requires inspected foreign-key and media effects. This route addition does not establish full-dashboard offline coverage.
