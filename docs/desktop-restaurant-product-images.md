# Scoped restaurant-product images

The reviewed desktop restaurant-product create/update/delete commands keep the original controller and Spatie FileAdder behavior. `DesktopDashboardProductImages` captures one optional `product_image` as its original filename, detected MIME, SHA-256 and immutable base64 bytes. The encrypted command and saved outcome retain this envelope. Each execution gets a disposable upload file; FileAdder may remove that temporary file without removing the durable command bytes. Native HTTP keeps Chromium's original multipart body unchanged.

New preview uploads accept PNG, JPEG and WebP, at most 5 MiB, at most 8192 pixels on either axis and at most 32 million pixels. Extension, actual MIME, image dimensions and digest must agree. SVG and other formats are explicitly unsupported for new preview uploads. Ordinary online forms retain their original validation. Existing reviewed raster media follow the scoped snapshot limits, with at most 50 media rows and 200 original/derivative files per product.

The helper accepts only the original `ResturantProduct` model, default Media model, FileNamer and PathGenerator, an empty prefix, no custom path generators, and the local `products` disk at `storage/app/public/products`. Every proof binds its raw media row to numeric media-ID paths, byte count, digest and MIME. No shared storage tree or external provider is inspected. Public product directories retain 0755 permissions on systems that use Unix permissions; private upload directories use 0700.

The whole original write, after-state capture and journal/outcome persistence transaction must run inside `ProductImages::guard`. After current actor/device/branch authorization, the adapter grants the exact product scope and independently checks the old file proofs before protecting its `product_image` rows. The scoped Spatie Filesystem suppresses physical deletion of those checked old files while original media rows still change in the database. New original image bytes are written completely, flushed, synced, installed at the original path and verified. A database, after-fact or journal failure therefore leaves old rows and bytes available after rollback. Scoped bindings and command state are restored in `finally`; ordinary online filesystem behavior remains unchanged.

Old replaced bytes and new files left by failed transactions are intentionally retained. No cleanup is claimed. Reviewed database writes require InnoDB, whose generated IDs are not reused after transaction rollback. Manual ID resets, media-path reuse and a conflicting existing target file fail closed with 503 while preserving existing bytes. SQLite rollback-ID reuse is outside this adapter's accepted database behavior. Machine power-loss persistence of new directory entries remains a separate acceptance check.

New desktop media UUIDs are valid UUIDv5 values derived from the command UUID and the single `product_image:0` slot. This keeps later command before-facts consistent across local and server media-ID translation. A trusted replay adapter supplies the local media creation/update time only after checking that it is within five seconds of the command occurrence. Spatie's default order counter uses the maximum across the whole media table, which may include server branches omitted from the local snapshot. Replay therefore also supplies the recorded new source-generated positive order after checking it exceeds the product's retained before-media orders outside `product_image`. Replaced `product_image` rows are excluded from that bound because the original repository deletes them before Spatie reads the global maximum. These fields are applied only to the newly inserted, scoped media row without process-global model listeners. Product creation time is validated separately by the CRUD adapter. Existing media UUIDs, timestamps and order values remain exact facts; ordinary online ordering retains the original global counter.

A saved response is reusable only after its original and derivative files still match their recorded proofs; missing or corrupt bytes return 503. An uploaded image must also match the saved sanitized filename, MIME, size and digest. Source-generated media IDs are translated explicitly, including the path prefixes, rather than ignoring media identity. Retention applies inside the current server or local generation: the current snapshot selects media belonging to existing scoped product rows, so media orphaned by the original query-delete and historical receipt files are not all carried into a later active local generation. Such a cached result may consequently fail its physical proof after refresh. No perpetual receipt-file retention across generations is claimed. Database and filesystem storage are not one atomic resource: retaining checked old bytes protects rollback, and physical proof checks expose incomplete new outcomes.

The implementation matches the actual packaged Spatie [9.12.4 Filesystem](https://github.com/spatie/laravel-medialibrary/blob/9.12.4/src/MediaCollections/Filesystem.php), [FileAdder](https://github.com/spatie/laravel-medialibrary/blob/9.12.4/src/MediaCollections/FileAdder.php) and [MediaObserver](https://github.com/spatie/laravel-medialibrary/blob/9.12.4/src/MediaCollections/Models/Observers/MediaObserver.php). FileAdder passes its sanitized original filename explicitly to `Filesystem::add`; media deletion otherwise removes physical bytes before the database transaction commits. The original model has no registered image conversions. Provider delivery is a separate scoped boundary and retains its documented best-effort limitations. This increment does not establish full-dashboard coverage; `fullDashboard=false` remains required.

## Ordered menu-copy image slots

The original parent-to-child menu-copy adapter also runs inside this guard. It authorizes each source product and new destination branch, then configures an ordered plan before invoking the original controller. Each actual first-image copy checks the current full source media row, original first-media choice, canonical disk path, display name, sanitized basename, actual MIME, dimensions and SHA-256. The new destination must be the exact freshly created product with no existing media. Source bytes remain intact through original FileAdder `preservingOriginal()` behavior. Ordinary online copying uses the original FileAdder with the corrected canonical source path and selected basename.

A copied first image receives UUIDv5 slot `menu_copy:<selection-index>:product_image:0`; repeated selections consequently have distinct slots. Only the trusted adapter can supply replay timestamps and order values after validating the original batch interval. The helper requires every planned slot to complete before after-facts and the outcome commit. One failed copy, after-state check or journal persistence rolls back every database change in the batch while retaining checked old files; new orphan-file cleanup and machine power-loss directory persistence remain outside this guarantee.

The preview accepts at most 100 selected products and 50 MiB of newly copied image bytes, with each copied PNG/JPEG/WebP at most 5 MiB. Generated `thumb` conversions, noncanonical source basenames and unreviewed disks/path generators fail before an accepted outcome. The complete before-state can contain other existing raster media, but its independent file/count/aggregate limits still apply. This does not copy every source media row or arbitrary API menu selections; the scoped menu adapter defines exact source-form coverage.
